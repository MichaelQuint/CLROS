Fast fixtures run in isolated worker processes with bounded parallelism (up to
four workers by default). Use `--jobs 1` for a serial comparison or `--jobs N`
to set the bound. A full run completes every selected fast case before starting
native work, including fast cases in otherwise native fixtures. Fast failures
are collected together and block the native phase; the receipt stays incomplete
and can be resumed after repair. Mixed fixtures have separate `.Fast` and
`.Native` checkpoint groups. Native fixtures execute exclusively because they
share native build outputs. Ordinary failures do not stop subsequent cases in
the active phase; a crashed or timed-out fixture does not stop other fixtures
when process cleanup is confirmed. Unconfirmed cleanup cancels remaining work and
drains already active workers before returning failure.
Output is bounded and streamed to disk immediately. Ctrl+C cancels the active
worker and writes an incomplete, unsuccessful receipt. Terminal success requires
paired case markers, a clean exit, and no failures. Logs and an updated `results.json`, including
the selected inventory, live under `artifacts/logs/host-tests/<run>/`.

Input checks run before each fixture launch/reuse and after every result,
including failed and non-cacheable native fixtures. A mismatch cancels queued
work, drains active workers through the same bounded cleanup, and immediately
invalidates this run's checkpoint entries. Late worker completion cannot restore
those entries. The final receipt remains unsuccessful and records the input
failure. Boundary checks compare file metadata, hash changed files, and check
the repository/source inventory and environment; they do not replace the exact
byte checks after cacheable passes and at completion. Edits that preserve file
metadata may only be caught by those exact checks. Stop the run before editing
or rebuilding; rebuild before resuming its retained failed receipt.

On the qualified Windows host, each child starts suspended, enters its owned
job, and then begins execution. Only its three standard-stream handles are
inherited. Root exit, cancellation, timeout, output overflow and capture failure
all require the job to be empty before returning; stdout and stderr remain
separate. Callback failures propagate after cleanup. This also prevents an early
parent exit from leaving descendants holding files or pipes. The generic
non-Windows process fallback cannot confirm the complete descendant tree and
reports that limitation as an unsuccessful result; it does not qualify host
acceptance evidence.

The build embeds source/dependency hashes and CI configuration. `--no-build`

### Resume an interrupted or failed host run

Every run saves `checkpoint.json` alongside `results.json`. `--results` selects
a new or empty directory. `--resume` accepts that directory or its receipt path
and inherits the previous lane and filters unless explicitly overridden. Rebuild
after editing tests; then resume the same directory. The exact selected cases,
their ordering, lane and `--case` filter form part of each worker group's key.
A focused or fast pass cannot satisfy a full/native selection of the same type.

For a test-only edit with unchanged production/tooling dependencies, use
`dotnet build tests/OS.HostTests --no-dependencies` before resuming. This preserves
the previously built dependency identities. Use a normal build when dependencies
changed or have not been built.

Failed, interrupted, new or invalidated groups execute again. An unchanged pass
emits `HOST_FIXTURE_REUSED` with its original run ID; its test markers are not
replayed. Receipts distinguish executed and reused groups/checks and retain the
original logs and host producer assembly. Completion rechecks compiled inputs,
source fingerprints and retained evidence. Missing or changed evidence prevents
reuse; corrupt receipts fail before launching fixtures. Directory and worker
leases prevent resuming an active run. Normal Ctrl+C still terminates workers.

Fingerprints include shared production/tooling/configuration/documentation,
producer dependencies, compiler options, runtime/SDK and environment identity
(digest only). Bound source dependencies distinguish namespaces, aliases,
nested identities and partial declarations. Global imports, assembly attributes
and actual source order participate in the key. The host DLL itself is retained
as provenance; non-source compiler inputs, including embedded input manifests,
remain conservative shared dependencies and can invalidate every cached group.

Reuse has a deliberately limited execution boundary. Only supported operations
whose reachable implementations are inspected in the current source catalog
are eligible. Opaque metadata calls or fields, external input, dynamic/virtual/
delegate/function-pointer dispatch, user operators, implicit calls and unknown
compiler operation forms execute fresh. A referenced DLL hash proves code
identity, not the state that code reads. Shared runner helpers receive the same
inspection when a fixture calls them. Source-only controls exercise real reuse;
metadata-dependent kernel fixtures still execute their behavioral checks.
Each fixture group executes in its own worker process; optional reuse does not
carry mutable static state between groups. [Step1693](../done/step1693.md)
records the focused dependency, resume and worker-protocol checkpoint.

Do not edit sources or share
native output directories between simultaneous suites. Checkpoints are local to
the same workspace and machine, and do not import legacy runner receipts.

The build manifest captures SDK-generated assembly attributes after generation.
Repository source globs use a normalized absolute root and exclude generated
`obj`, `bin` and `artifacts` trees. The harness's own generated compiler inputs
and reference DLLs remain dependencies; real application JSON configuration is
also retained. Rebuilding an app must not turn its transient Razor caches into
host-test source inputs. Genuine source/configuration changes still fail closed.
Pointer-probe and finally-guard builds use `--no-dependencies` so they cannot rebuild libraries
already admitted by the running harness. Step1117 records the commit-version
staleness failures that led to these fixes and their focused checks.

Native output ownership is deliberately explicit. The owned-IDT group and the
individually selected IDTR publication case produce every artifact they read. Their keys also
hash the resolved SDK, linker/support files, Windows library, LLVM, runtime and
pinned package contents. Twelve original outputs per publication fixture are
copied into content-addressed storage; later builds cannot overwrite that
evidence. Ownership is necessary but does not override the execution boundary:
opaque implementations still run fresh. The full IDTR group and other
unclassified native groups execute fresh. Retained publication records are
historical host evidence, not restored canonical build outputs or new guest
execution. Broader native reuse requires both reviewed input/output ownership
in `HostNativeResumePolicy` and a demonstrated execution/input boundary.

Verify the EFI publish:

```powershell

```

Expected current success markers:

```text
TEST_PASS efi.shell.publish
EFI_ARTIFACT artifacts/efi/BOOTX64.EFI
```

`OS.Tooling efi build` runs a host-toolchain preflight before
`dotnet publish`. The preflight resolves the MSVC x64 `link.exe`
(`Hostx64\x64`) and the Windows SDK UM x64 `kernel32.lib` (`um\x64`) using
`vswhere` plus well-known install roots, and it emits:

```text
EFI_PREFLIGHT_START
EFI_PREFLIGHT_MSVC_LINKER <path>
EFI_PREFLIGHT_WINDOWS_SDK <path>
EFI_PREFLIGHT_OK
```

If a prerequisite is missing, the script fails before `dotnet publish` with a
deterministic reason and the log path, without dumping host environment data:

```text
TEST_FAIL efi.shell.publish platform_linker_missing log=artifacts/logs/efi-shell-publish.log
TEST_FAIL efi.shell.publish windows_sdk_um_x64_missing log=artifacts/logs/efi-shell-publish.log
```

This preflight is host-toolchain evidence only. `EFI_PREFLIGHT_OK` proves that
the linker and SDK library files are discoverable on this host. It does not
prove a successful publish, a staged `artifacts/efi/BOOTX64.EFI`, QEMU boot,
`ExitBootServices`, or any runtime behavior. The search roots are injectable
through `-MsvcLinkerSearchRoot`, `-WindowsSdkLibSearchRoot`, and `-VsWherePath`,
and `-PreflightOnly` runs the checks without publishing so host tests can cover
the contract with fakes instead of uninstalling toolchains.

## Windows CI Agent Bring-Up

Use this section as the canonical host-prerequisite checklist for a Windows CI
agent. It documents the agent shape and validation commands only; it does not
create a repository CI workflow and does not turn dry-run evidence into boot
proof.

Required agent capabilities:

- Windows 10 or Windows 11 x64 with PowerShell 5.1 or newer.
- Exact .NET SDK `11.0.100-rc.3.26522.148`, with prerelease admission and no roll-forward as governed by `global.json`.
- Visual Studio or Build Tools with `Microsoft.VisualStudio.Workload.VCTools`
  and `Microsoft.VisualStudio.Component.VC.Tools.x86.x64`.
- Windows 10/11 SDK UM x64 libraries, including `kernel32.lib`.
- QEMU for dry-run command discovery and optional real smoke:
  `qemu-system-x86_64.exe`, `qemu-img.exe`, and an OVMF code image such as
  `edk2-x86_64-code.fd`.

Prefer explicit script parameters on CI agents so logs show the intended tool
inputs without dumping PATH contents:

```powershell
$qemu = "C:\Program Files\qemu\qemu-system-x86_64.exe"
$qemuImg = "C:\Program Files\qemu\qemu-img.exe"
$ovmf = "C:\Program Files\qemu\share\edk2-x86_64-code.fd"
```

When explicit parameters are not practical, current discovery also supports
`QEMU_IMG` for `qemu-img`, `OS_OVMF_CODE`/`OVMF_CODE`/`QEMU_OVMF_CODE` for
OVMF, PATH lookup for QEMU tools, and the well-known QEMU install paths listed
above. Do not print environment dumps, PATH contents, package feed tokens, or
other secrets in CI logs.

Minimum non-boot CI agent validation:

```powershell
dotnet --info
dotnet build .\CLROS.slnx --nologo -m:1
dotnet run --project tools/OS.Tooling -- efi build -PreflightOnly
dotnet run --project tools/OS.Tooling -- qemu smoke -DryRun
dotnet run --project tools/OS.Tooling -- ci smoke --dry-run
dotnet run --project tools/OS.Tooling -- baseline evidence --plan-only
git diff --check
```

The first repository workflow for this lane is
`.gitea/workflows/ci-smoke.yml`. It targets a Windows runner labelled
`windows` and runs the non-boot validation commands above, then attempts to
upload `artifacts/logs/**` when the runner supports `actions/upload-artifact`.
Adjust only the runner label or artifact action source for local Gitea runner
policy; keep the default lane dry-run/preflight/plan-only until a separate
issue captures real QEMU/qcow2 smoke evidence. Host tests guard this workflow
contract so the default lane keeps the expected triggers, PowerShell shell,
timeout, upload-on-failure behavior, commands, and absence of real-smoke flags.
`OS.Tooling ci smoke` also plans and captures `git diff --check` as
`ci.smoke.git.diffcheck`, so whitespace evidence is present in the CI smoke
artifact plan and summary.

TEST_START ci.smoke.qemu_img.discovery

## Unsupported Behavior

The host requirements above only prove build and publish prerequisites. They do not prove QEMU boot, ExitBootServices, drivers, storage, networking, hosted .NET applications, ASP.NET Minimal API hosting, or Kestrel.

Linux/macOS hosts are not documented for the EFI publish path yet. A future cross-build path can be added after the Windows NativeAOT/EFI path is stable.

## Known Limitations

- `artifacts/efi/BOOTX64.EFI` plus `artifacts/images/os.raw` now prove only the EFI smoke path, ordered boot markers, and UEFI memory-map readiness marker, not a functional kernel.
- QEMU and OVMF are required only for real smoke runs; dry-run and host unit tests still work without them.
- Hyper-V is not required for build or publish. Windows QEMU selects WHPX by default; use `-Accelerator tcg` explicitly for software emulation. Other hosts default to TCG. An unavailable WHPX selection fails clearly.
- The current EFI shell uses placeholder no-stdlib runtime helpers that are not a complete runtime contract.
