The lifecycle owner enforces these operations together:

| Operation | Required ownership behavior |
| --- | --- |
| Create/start | Fully initialize stack, context and entry metadata before publishing runnable state. Roll back every allocation/admission/publication failure. |
| Yield/park/wake | Serialize state, queue and lifetime changes in one save/disable/restore-IF transaction. A generation-tagged thread ID and a distinct wait identity prevent old completions from ending a later wait. |
| Sleep | Use checked ticks in one nonwrapping epoch; delay zero yields. Preserve or reserve ready capacity before consuming a due deadline. |
| Join | Allow one pending waiter per target. Reject self-join, cyclic joins and a second waiter explicitly. Keep the completion status observable by repeated completed joins until supervisor reap. |
| Cancel | Request cancellation; observe it at start or a cooperative safe point. Resume a parked worker with a cancellation result so it reaches its exit path. Cancelling a join wait does not cancel its target. |
| Exit/reap | Transfer to the retained supervisor stack before releasing worker storage. Remove all ready/deadline/join and IRQ/context lifetime references, then scrub/release and advance the slot generation. Identity exhaustion fails closed. |

### Saved-context host contract (#183)

[Step1210](../done/step1210.md) records nine focused checks for
`Threading/X64ThreadContext.cs`. This is a 688-byte unmanaged value in a live,
caller-owned buffer whose address must be 16-byte aligned. Natural CLR struct
alignment does not provide that guarantee. All scalar fields below are eight
bytes; the final field is a 512-byte FXSAVE64 image.

| Field | Byte offset |
|---|---:|
| Private completion version / reserved | 0 / 8 |
| RAX / RBX / RCX / RDX | 16 / 24 / 32 / 40 |
| RSI / RDI / RBP / RSP | 48 / 56 / 64 / 72 |
| R8 / R9 / R10 / R11 | 80 / 88 / 96 / 104 |
| R12 / R13 / R14 / R15 | 112 / 120 / 128 / 136 |
| RIP / RFLAGS / FS base / user-GS base | 144 / 152 / 160 / 168 |
| FXSAVE64 image | 176 |

Within the FP image, x87 control is at 0, MXCSR at 24, MXCSR_MASK at 28,
eight 16-byte x87/MMX slots start at 32, and sixteen 16-byte XMM slots start
at 160. Initial controls are x87 `0x027f` (Win64 double precision, masked
exceptions) and MXCSR `0x1f80`. The caller supplies an independently trusted
CPU MXCSR_MASK observation: zero uses Intel's `0xffbf` fallback; a nonzero
mask must fit 16 bits and permit the initial MXCSR. The saved mask must equal
that observation, and saved MXCSR cannot set bits outside its effective mask.
The image cannot authorize additional features by widening its own mask.
These rules follow the [Intel SDM](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html)
(volume 1, sections 10.5.1 and 11.6.6) and the
[Win64 calling convention](https://learn.microsoft.com/en-us/cpp/build/x64-calling-convention?view=msvc-170).

`Initialize`, read-only `Validate`, and overlap-safe `Copy` use status results,
exclusive ownership and no allocation. Shape checks reject null, short,
misaligned, overflowing or noncanonical declared buffers before access;
valid-looking pointers still require the caller to provide mapped storage.
RIP/RSP must be nonzero four-level canonical addresses; FS/user-GS may be zero.
Both canonical halves are structurally admitted. RFLAGS requires bit 1 and
permits only `0x00250fd7`; IOPL, NT, virtual-mode and reserved bits are rejected.
All fallible checks precede the destination copy, so failure preserves every
destination byte. The private version/reserved pair marks software completion
under exclusive ownership; it is neither concurrent publication nor restore
authority. Captured x87/data bytes are opaque state, not fresh initialization.

Thread values include FS and user-GS bases. Selectors, address-space root,
kernel-GS and TSS remain with the trusted CPU/transition owner, which must
separately admit executable mappings, privilege, stack ABI/ownership, TLS
lifetimes and CPU features before restore. Cooperative Win64 calls preserve
callee-saved registers; asynchronous interruption requires all interrupted
state. SYSCALL transforms RCX/R11 into return RIP/RFLAGS; the existing M16
syscall frame and normalized fault frame retain their distinct formats.
This ticket executes no FXSAVE/FXRSTOR, privileged transfer or live FS/TLS
setup. Actual switching, interrupt preservation, Linux threads and later
runtime acceptance remain deferred.

Actual cooperative transfer belongs to #186, hardware interrupt wake/preemption
to #187, and thread lifecycle to #188. These retain default-off guest profiles,
original native review and final-source qualification. A cooperative ABI context
or Linux syscall frame is not automatically a complete interrupted-thread
context. The initial profile retains the existing single-CPU x87/SSE boundary;
XSAVE/AVX, CET and SMP require separate admission and evidence. Upstream Linux
thread/TLS/futex/signal integration remains in M16.

boundary is documented here and in `work/PAL/pal-design.md`. The upstream

## ABI Naming

The first-party PAL ABI prefix is `OSHost_*`.

Example first-party symbols:

- `OSHost_AllocPages`
- `OSHost_FreePages`
- `OSHost_ProtectPages`
- `OSHost_QueryMemory`
- `OSHost_GetMonotonicTicks`
- `OSHost_WriteLogBytes`
- `OSHost_GetRandomBytes`
- `OSHost_OpenPackageFile`
- `OSHost_ReadBlock`

Migration rule for adapted reference code:

1. Rename `SharpOSHost_Foo` to `OSHost_Foo` when adding first-party declarations, exports, tests, or docs.
2. Keep the suffix stable unless a separate design note explains the contract change.
3. Add a `SharpOSHost_*` alias only when a documented compatibility dependency cannot be migrated at the same time.
4. Treat any alias as an adapter, not as the canonical OS ABI.

## ABI Rules

All first-party PAL calls must obey these rules:

- Function names use the `OSHost_*` prefix.
- Every function returns an `OSHostStatus` value.
- Outputs are returned through unmanaged out pointers or caller-provided buffers.
- Handles are opaque unsigned 64-bit values. Handle value `0` is invalid.
- Pointers identify unmanaged memory only and must be paired with explicit byte lengths.
- Strings are UTF-8 byte spans. They are not managed `string` references and must not rely on null termination.
- Structs are fixed-layout POD contracts with explicit integer fields, byte arrays, offsets, lengths, handles, and flags only.
- No managed references, object references, delegates, exceptions, C++ objects, host pointers to movable memory, or allocator-owned buffers cross the ABI.
- A function that cannot complete synchronously must return a status such as `OSHOST_STATUS_WOULD_BLOCK`, `OSHOST_STATUS_TIMED_OUT`, or use an explicit waitable handle contract. It must not block forever.
- Release builds must not return secret config values in diagnostics or panic text.

## Kestrel-Critical ABI

This section defines the minimum PAL surface needed before ASP.NET Minimal API/Kestrel can be attempted in guest. The C# declaration structs above are layout declarations only, and no declaration-only test is Kestrel support evidence.

PAL-local claim boundary: the declaration structs and mock tables/facades in this document are host-tested in-process contract models only. They do not export unmanaged `OSHost_*` symbols, run in the guest, allocate real pages, mutate page tables, schedule or wake threads, read guest storage, move network packets, integrate CoreCLR/hosted .NET 10, run ASP.NET Minimal API, or prove Kestrel. See [docs/completion-gates.md](completion-gates.md) for full gate status and evidence requirements.

### Socket Domain

Kestrel v1 requires an inbound TCP stream listener. UDP, DNS, TLS, HTTP/2, HTTP/3, and WebSockets are out of scope for the first Kestrel proof unless separate issues implement them.

POD contracts:

- `OSHostHandle`: opaque `ulong` used for socket handles.
- `OSHostSocketAddress`: address family, port in network byte order, scope id, and 16 address bytes so IPv4 and IPv6 fit the same struct.
- `OSHostSocketCreateOptions`: domain, type, protocol, nonblocking flag, reserved flags, and struct version.
- `OSHostSocketIoRequest`: socket handle, caller-owned buffer, and flags for future send/receive calls.
- `OSHostSocketPollEntry`: readable, writable, error, hangup, accepted-connection flags, and per-socket status for future poll calls.
- `OSHostSocketBindRequest`: socket plus manifest-approved local address for bind.
- `OSHostSocketListenRequest`: socket plus backlog for listen.
- `OSHostSocketAcceptRequest` and `OSHostSocketAcceptOutput`: listener, timeout, accepted socket handle, and endpoint metadata for accept.
- `OSHostSocketConnectRequest`: socket plus remote address and timeout for future outbound connect.
- `OSHostSocketShutdownRequest`: socket plus receive/send/both shutdown direction.
- `OSHostSocketOptionRequest`: socket option name/value pair for Kestrel-oriented options.
- `OSHostSocketAddressQueryRequest`: socket plus local-or-remote address kind for endpoint queries.
- `OSHostTimeout`: timeout kind and monotonic deadline/tick count.

Required functions:

- `OSHost_SocketCreate`
- `OSHost_SocketBind`
- `OSHost_SocketListen`
- `OSHost_SocketAccept`
- `OSHost_SocketConnect`
- `OSHost_SocketSend`
- `OSHost_SocketReceive`
- `OSHost_SocketShutdown`
- `OSHost_SocketClose`
- `OSHost_SocketSetOption`
- `OSHost_SocketGetLocalAddress`
- `OSHost_SocketGetRemoteAddress`
- `OSHost_SocketPoll`

First Kestrel-compatible behavior:

- IPv4 TCP stream sockets.
- Bind to a manifest-approved local address and port.
- Listener access is denied by default. A hosted app receives network listener capability only through manifest/supervisor policy; no ambient POSIX-style bind permission exists.
- Listen backlog with a documented maximum.
- Accept inbound connections without allocating in the ABI call.
- Connect metadata for already-bound outbound IPv4 TCP stream handles; the host mock records remote endpoint metadata only.
- Send and receive caller-owned byte buffers.
- Nonblocking or bounded wait semantics for accept/read/write.
- `NoDelay`, `ReuseAddress`, receive timeout, send timeout, and keep-alive options as status-coded contracts.
- Endpoint queries for the bound local address and accepted peer address.
- Deterministic `ReuseAddress` policy: duplicate binds are rejected unless the new socket and every conflicting bound/listening socket have `ReuseAddress` enabled.
- Cancellation through timeout, socket close, or wait interruption.
- Deterministic close and shutdown behavior.

### Timer Domain

Kestrel and the hosted runtime need monotonic time for request timeouts, keep-alives, cancellation, thread-pool scheduling, and log timestamps.

POD contracts:

- `OSHostTicks`: unsigned 64-bit monotonic tick count.
- `OSHostTickFrequency`: unsigned 64-bit ticks per second.
- `OSHostHandle`: opaque `ulong` used for timer handles and optional completion wait handles.
- `OSHostTimeout`: timeout kind, flags, tick value, and tick frequency.
- `OSHostTimerOptions`: one-shot/periodic flags, due tick/deadline, period ticks, and optional completion wait handle.

Required functions:

- `OSHost_TimeGetMonotonicTicks`
- `OSHost_TimeGetTickFrequency`
- `OSHost_TimeGetWallClockUnixNanoseconds`
- `OSHost_TimerCreate`
- `OSHost_TimerArm`
- `OSHost_TimerCancel`
- `OSHost_TimerClose`
- `OSHost_ThreadSleepUntil`

First Kestrel-compatible behavior:

- Monotonic ticks never move backward.
- Frequency is stable for the boot session.
- Wall-clock may be unavailable and must return `OSHOST_STATUS_NOT_SUPPORTED` rather than fabricating time.
- Timeout/deadline comparison is status-coded: invalid timeout kinds or mismatched tick frequencies return `OSHOST_STATUS_INVALID_ARGUMENT`, infinite timeouts remain pending forever, immediate timeouts are expired at the current tick, and absolute deadlines report pending or expired relative to monotonic ticks.
- Timer wait wakes are visible to `OSHost_WaitOne` or `OSHost_WaitMany`.
- Sleep and timer APIs have bounded failure behavior during shutdown.
- `OSHostTimerTable` currently models one-shot/periodic timer semantics and completion wait-handle preservation in host tests only. `OSHostTimerWaitBridge` can set a mock wait event after polling a due timer, but it does not block or park threads, wake scheduler threads, program hardware timers, deliver interrupts, export PAL functions, or implement `Task.Delay`.

### Thread And Sync Domain

Single-thread stubs are not enough for Kestrel. The hosted runtime needs threads, blocking waits, wakeups, memory ordering, and synchronization primitives that can support a thread pool.

POD contracts:

- `OSHostHandle`: opaque `ulong` used for thread handles and wait handles.
- `OSHostThreadId`: unsigned 64-bit id.
- `OSHostThreadStart`: unmanaged code pointer-as-integer plus unmanaged context pointer-as-integer.
- `OSHostThreadCreateOptions`: stack size, guard size, priority class, name UTF-8 span, and flags.
- `OSHostWaitOneRequest`: single wait handle, timeout, and flags.
- `OSHostWaitManyRequest`: caller-owned wait-handle span, timeout, and flags.
- `OSHostWaitResult`: signaled index, timeout, interrupted, abandoned, or failed status.

Required functions:

- `OSHost_ThreadCreate`
- `OSHost_ThreadExit`
- `OSHost_ThreadJoin`
- `OSHost_ThreadYield`
- `OSHost_ThreadGetCurrentId`
- `OSHost_WaitOne`
- `OSHost_WaitMany`
- `OSHost_EventCreate`
- `OSHost_EventSet`
- `OSHost_EventReset`
- `OSHost_EventClose`
- `OSHost_SemaphoreCreate`
- `OSHost_SemaphoreRelease`
- `OSHost_SemaphoreClose`
- `OSHost_MutexCreate`
- `OSHost_MutexLock`
- `OSHost_MutexUnlock`
- `OSHost_MutexClose`
- `OSHost_MemoryBarrier`

First Kestrel-compatible behavior:

- Hosted runtime can create at least two managed worker threads.
- Thread join and wait APIs cannot deadlock the kernel when a thread exits or panics.
- Manual-reset and auto-reset event modes are explicit.
- Semaphore count overflow is status-coded.
- Wait-many has a documented maximum handle count.
- Memory barriers and atomic operations are sufficient for runtime synchronization. Atomic primitives may live in runtime helpers, but their ABI relationship must be documented before hosted runtime integration.
- `OSHostThreadTable` currently models thread-create option validation, opaque thread handles, deterministic thread ids, immediate join-after-exit, current-thread id, yield status, early single-thread capability metadata, immediate-only sleep completion, unsupported blocking sleep status, capacity exhaustion, handle reuse, and default/zero result rejection in host tests only. It does not allocate stacks, start code, context switch, block, schedule, join real execution, or satisfy hosted .NET/Kestrel threading requirements.
- `OSHostWaitTable` currently models immediate wait/event semantics in host tests only. It rejects malformed timeout structs as invalid arguments, reports valid non-immediate waits as unsupported in the current early single-thread mode, exposes capability metadata that is not hosted-runtime readiness, rejects default/zero event-create and capability results as success evidence, and can be signaled by the host-only timer/wait bridge after an already-due timer poll, but it does not block, park threads, integrate hardware timers, wake scheduler threads, implement `Monitor`, or satisfy `Task`/ThreadPool/Kestrel runtime requirements.
- `OSHostWaitFacade` currently models future exported wait/event call status translation over that table in host tests only. It does not export unmanaged symbols, block, park threads, wake scheduler threads, integrate hardware timers, or satisfy hosted .NET/Kestrel synchronization requirements.

Kestrel and ASP.NET configuration need deterministic package and manifest access. The first version is read-only and package-scoped.

POD contracts:

- `OSHostFileHandle`: opaque `ulong`.
- `OSHostFileInfo`: length, attributes, content kind, modified timestamp if available, and flags.
- `OSHostPackagePath`: UTF-8 relative package path byte span.
- `OSHostConfigKey`: UTF-8 manifest/config/environment key byte span.
- `OSHostConfigValue`: UTF-8 value byte span copied into caller buffer.

Required functions:

- `OSHost_OpenPackageFile`
- `OSHost_ReadFileAt`
- `OSHost_GetFileInfo`
- `OSHost_CloseFile`
- `OSHost_EnumeratePackage`
- `OSHost_GetConfigValue`
- `OSHost_EnumerateConfig`
- `OSHost_GetEnvironmentValue`
- `OSHost_EnumerateEnvironment`
- `OSHost_WriteLogBytes`

First Kestrel-compatible behavior:

- Hosted runtime reads app assembly, deps/config files, `appsettings*.json`, and optional static content from the package.
- The first Minimal API smoke package contract, `kestrel.smoke.package.v0`, requires package-relative reads for `apps/minimal-api/MinimalApiSmoke.dll`, `apps/minimal-api/MinimalApiSmoke.deps.json`, `apps/minimal-api/MinimalApiSmoke.runtimeconfig.json`, and `apps/minimal-api/appsettings.json`.
- Paths are relative to the package root and reject absolute paths, drive prefixes, device paths, and `..` traversal.
- File reads are offset-based and do not depend on shared mutable seek state.
- Config and environment values are supplied by the manifest, not host OS environment variables.
- The first smoke package requires `OSHost_GetEnvironmentValue` or an equivalent documented config path to surface `OS_SMOKE_EXPECTED_BODY=OS_MINIMAL_API_OK` to the hosted app before `GET /healthz` can be accepted as Kestrel evidence.

- Buffer sizing uses `OSHOST_STATUS_BUFFER_TOO_SMALL`; the OS does not allocate return buffers for the hosted runtime.
- App stdout/stderr and ASP.NET logs flow through `OSHost_WriteLogBytes` to OS serial/logging policy.

## Unsupported Behavior

All hosted-tier PAL domains are pending implementation: memory, time, console/log, entropy, file/block, thread/sync, exception/unwind, environment/config, and socket/network boundary.

The Kestrel-critical memory, socket, timer, thread/sync, file/config, logging, and entropy function families are documented only. Initial POD declaration structs exist, and current mock memory, socket, package-file, config/environment, timer, wait, app-log, and random tables are host-tested in-process models only. No hosted runtime consumes them.

Most UEFI platform interfaces are still pending:

- `IPlatformKeyboard`

## Known Limitations

`work/PAL/pal-design.md` is a baseline document, not an implementation. The
upstream reference PAL design lives under `references/SharpOS-main/work/PAL/`;
its architecture does not override the CLROS boundary.

The Kestrel-critical ABI list is intentionally minimal. It does not include TLS, certificates, HTTP parsing, HTTP/2, HTTP/3, WebSockets, QUIC, filesystem writes, dynamic package mutation, host process APIs, or POSIX-style file descriptors.

The socket ABI value contracts, mock socket table, socket facade, manifest bind/listen bridges, TCP listener backlog socket bridge, and TCP established-stream socket bridge are host-tested in-process models only. Partial I/O, peer close, peer reset, poll readiness, mock listener creation, host-only connect metadata over already-bound handles, default/zero socket-create, accept-result, poll-result, and operation-result rejection, backlog-to-accept-queue composition, and established-payload inbound queueing are local mock semantics; they do not export PAL symbols, implement DNS/routing/TCP handshakes/FIN/RST packets, block or wake scheduler waits, or move network traffic.

The timer table, timer facade, and timer/wait bridge are host-tested in-process models only. Their timeout/deadline comparison, completion wait-handle preservation, mock event signaling, and future-export-shaped status translation are local to the mock monotonic tick source and mock wait table; they do not schedule real wakes, program APIC/HPET/TSC timers, deliver interrupts, wake scheduler threads, or implement `Task.Delay`.

The thread table is a host-tested in-process model only. Its create-option validation, deterministic thread id allocation, lifecycle state, exit-code recording, current-id result, yield status, early-mode capability metadata, immediate-only sleep completion, unsupported blocking sleep status, handle reuse, capacity exhaustion, and default/zero result rejection are local mock semantics; it does not allocate stacks, create scheduler threads, switch contexts, invoke entrypoints, block or wake joins/sleeps, integrate TLS/thread statics, implement `Thread`, `ThreadPool`, `Task`, or export PAL symbols.

The wait table and wait facade are host-tested in-process models only. Their manual-reset, auto-reset, immediate wait-one/wait-any, cancellation, close, invalid/stale-handle rejection, unsupported wait-all rejection, malformed timeout rejection, non-immediate timeout rejection, early-mode capability metadata, default/zero event-create and capability-result rejection, null-table rejection, capacity semantics, and timer-bridge event readiness are local behavior; they do not block, park or wake scheduler threads, consume hardware timer completions, implement `Monitor`, or satisfy ThreadPool waits.

The app-log table and facade are host-tested in-process models only. Their stdout/stderr stream ids, bounded byte writes, machine-readable marker preservation, request-shape validation, and deterministic rejection paths are local behavior; they do not write guest serial output, connect hosted runtime console streams, or capture real app exit status.

The random table and facade are host-tested in-process models only. Their deterministic byte stream, unavailable-entropy status, request-shape validation, and default-result rejection are local behavior; they do not call firmware RNG, seed a post-firmware entropy pool, export `OSHost_GetRandomBytes`, provide cryptographic randomness, feed hosted runtime hash/randomization, or satisfy TLS/certificate requirements.

The package-file table and facade are host-tested in-process models over already-loaded package bytes only. They reject invalid, unknown, and closed handles through status codes and model future file-call status translation; they do not perform guest block I/O or enumerate package directories from live storage.

The config/environment table and facade are host-tested in-process models over caller-provided byte entries or a host-provided native launch plan only. The listen endpoint config keys are source-backed metadata projection only. The table's caller-buffer byte copies are source-guarded to use `OS.Std.Memory.BufferOperations.MemoryCopy`, but it still only models future config/environment status translation; it does not export PAL symbols, read guest storage, feed hosted .NET configuration, ASP.NET configuration, or process environment variables.

The memory-protection plan, memory table, and memory facade are host-tested in-process validation models only. They do not allocate or free real pages, update page tables, flush instruction caches, create executable mappings, integrate the GC, or prove live W^X/NX enforcement.

`OSHostStatusNameFormatter`, `OSHostStatusCategoryFormatter`, and `OSHostStatusContract` are host-tested caller-buffer diagnostic/status-contract helpers only. The status-name, status-category, and status-domain formatter writes are source-guarded to use the shared `AsciiTextBuilder.AppendBytes` append path, but they do not export PAL diagnostic functions, expose status text/categories/contracts to a hosted runtime, write serial output, allocate managed or unmanaged return buffers, or prove hosted .NET diagnostics.

UEFI encapsulation is a prerequisite for later PAL and hosted-tier work, but it is not itself evidence of hosted .NET 10, Minimal API, or Kestrel support.

`IPlatformMemoryMap` is an encapsulation guardrail only. The host tests use a guarded test double and do not prove live UEFI descriptor copying, OS-owned memory-map storage, or `ExitBootServices`.

`IPlatformConsole` is an encapsulation guardrail only. The host tests use
`GuardedPlatformConsole` with a counting sink and do not prove live UEFI
`OutputString`, serial fallback, owned post-firmware serial output, or integration
with `EfiEntry`.

`IPlatformTimer` is an encapsulation guardrail only. The host tests use an injected metadata source and do not prove HPET, APIC timer, TSC calibration, scheduler wakeups, `Task.Delay`, hosted .NET timers, or Kestrel timeout behavior.

`IPlatformFileSystem` is an encapsulation guardrail only. The host tests use an injected read-only source and do not prove UEFI Simple File System Protocol wiring, disk-backed package loading, directory enumeration, filesystem writes, app execution, hosted .NET, or Kestrel.

`PhysicalMmioOwnershipPlan` is host-tested planning metadata only. It does not reserve physical ranges in a live allocator, create page-table mappings, set cacheability attributes, dereference ECAM, perform volatile MMIO, enumerate PCI, or prove cloud-provider hardware support.

`FirmwareServicesGuard` currently proves host-side state behavior only. It does not yet stop real firmware calls in the no-stdlib EFI artifact. The default QEMU smoke path stays normal, while the explicit simulation artifact exercises `UEFI_GONE_SIM_START`, `UEFI_GONE_SIM_PLATFORM_DENIED`, `POST_FIRMWARE_DIAGNOSTICS_READY`, and `UEFI_GONE_SIM_PASS`.

`UefiExitBootServicesPlan` and `BootSequence.RunExitBootServicesTransition` are not firmware-shutdown evidence. They only define deterministic retry and marker decisions for a future implementation that will repeatedly capture a fresh memory map, call firmware, and retry on stale map-key rejection.

`PlatformFirmwareExitBootServicesResult` is not firmware-shutdown evidence. It only records how the future live call result will be status-coded after guard and function-pointer checks.

`UefiExitBootServicesLiveWiringPlan` is not firmware-shutdown evidence. It documents and host-tests the intended live call order, but the real `EfiEntry` path still does not call `ExitBootServices`.

`EnableExitBootServicesFreshMapProbe` is disabled by default. The explicit EFI probe build does call `GetMemoryMap` again before the future shutdown point and proves `UEFI_EBS_CALL_SKIPPED`; it still does not call `ExitBootServices`, does not change `FirmwareServicesGuard`, and is not evidence of a successful boot-services shutdown.
