## Known Limitations

The current order is still a marker contract, not a full hardware boot sequence. It does not prove owned drivers, interrupts, page tables, storage, networking, or hosted workload launch.

The M02-009 byte contract is not a firmware-visible `BootSequence` phase. Its
host marker correctly reports the live properties as false for the isolated
leaf, while the separately merged default-off EFI profile now provides the
accepted source-bound guest `lgdt`/`ltr`, owned COM1, terminal-halt, and
QEMU/OVMF evidence. That terminal profile remains pre-`ExitBootServices`, runs
after the ordinary smoke-success marker, and proves no IDT installation, live
fault handling, post-firmware operation, or change to the default order.

The M02-010 page is likewise not a firmware-visible `BootSequence` phase. The
leaf's exact host marker reports all four live properties as false. The
separate default-off EFI profile now supplies bounded QEMU/OVMF evidence for
guest page allocation, materialization, production readback, and release before
memory-map capture, but it does not publish executable memory, enter a slot or
common target, install an IDT/IDTR/IST, normalize a live CPU frame, or trigger a
fault. Its auxiliary profile cannot be promoted to a change in the default
boot order.

The M02-011 IDT page is also not a firmware-visible `BootSequence` phase. Its
host marker proves deterministic caller-owned bytes and readback. The separate
default-off EFI profile now supplies bounded QEMU/OVMF evidence for temporary
three-page allocation, M02-010 slot materialization/readback, M02-011 IDT
population/readback, and release before memory-map capture. It does not publish
executable slots, load IDTR, activate GDT/TSS/IST state, enter a slot/common
target, deliver an interrupt, or trigger a fault. Its auxiliary profile cannot
be promoted to a change in the default boot order.

The M02-012 reversible IDTR profile is likewise not a firmware-visible
`BootSequence` phase. It runs only under its default-off EFI switch before
ordinary memory-map capture, and its success record states that the temporary
owned IDTR is inactive and all allocations are released on return. If exact
loaded-IDTR, raw restoration, non-owned previous IDTR, or IF restoration cannot
be verified after entry, it deliberately spins without firmware output or
cleanup callbacks. This bounded profile does not establish interrupt/fault
delivery, executable common dispatch, persistent descriptor state, active
GDT/TSS/IST routing, post-`ExitBootServices` operation, or a numbered-gate
promotion.

The M02-013 terminal profile is also not a firmware-visible `BootSequence`
phase. It is entered only after `OS_SMOKE_PASS` under its default-off EFI switch
and never returns after the deliberate invalid-opcode fault. Its accepted tuple
proves that one recorded QEMU CPU delivered vector 6 to the fresh owned IDT,
used the owned GDT/TSS state, captured and matched the requested integer/control
state, and emitted the exact owned-COM1 terminal transcript. LoaderCode is an
allocation type, not evidence of live W^X enforcement. The profile supplies no
cleanup or descriptor-restoration observation after entry and proves no safe
continuation, persistent descriptor state, post-`ExitBootServices` operation,
