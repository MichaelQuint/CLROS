# Step1598 - Restricted kernel and workload qualification guardrails

## What changed and why

The user requested durable guidance to limit freestanding NativeAOT maintenance
and keep development focused on the .NET appliance product. The agent guide now
requires a demonstrated product need before expanding kernel runtime features,
retains upstream guest GC/EH/BCL behavior and reusable core OS services, requires
automated compiler-dependent inspection, and measures capability through complete
guest scenarios alongside focused verification.

Normal compatible app publication/rebuild/deployment must not depend on manual
disassembly, reference-VM analysis or per-app kernel/verifier allow-list changes.
Package integrity hashes and immutable diagnostic evidence remain distinct from
that prohibited deployment dependency. Existing general-hosting successors own
implementation of the generic route.

The scenario criteria cover real static-file/Blazor service, persistent HTTP
uploads, direct Microsoft.Data.Sqlite transactions/recovery, and two-app isolation.
They preserve the existing dependency graph and historical finite gate scopes.
The failure workflow requires identifying the first failed invariant, accounting
for observer interference, and making a bounded repair before expensive reruns.
