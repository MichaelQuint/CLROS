# Step 1240 - Retained futex memory mutation guard

## Summary

Development stage for #686/#733, parent
`5849c7516f9682edbb1db0c123cb0d702773a6f1`, draft PR #732. LAN repository

LinuxMemoryServices can now attach an exclusive retained-memory guard. Its
existing Apply commit point checks every changed live interval before zeroing
backing, publishing tables or changing accounting. The real host futex/table
owner refuses changes intersecting waits, including woken completions whose
backing reference is still retained. The actual EFI owner still must attach it.

## Why

Step1237's MayChangeUserRange query alone could not protect memory mutations.
The backend now enforces that query at the common commit point for unmap,
fixed replacement, protection, discard, remap and heap resize. Region-boundary
comparison preserves unchanged physical offsets/protection and splits at the
fresh-data boundary. Unrelated changes and unchanged remap prefixes remain
usable; dump-policy-only changes do not invalidate backing.

Attachment is explicit and preserves existing unguarded behavior. Guarded
state binds its actual address, rejecting copies. Detachment authenticates the
exact callback/context and requires a final whole-user-range query to confirm
all retained borrows are gone. The native owner must stop publication and drain
threads before detaching/releasing callback storage. The guard is read-only,
nonreentrant and externally serialized under the existing inactive-root/IRQ-off
contract. Rejection returns ENOMEM; raw brk retains its original break. Candidate
table scratch may change, but live tables/state/data remain unchanged.
