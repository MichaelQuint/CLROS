# Step 1055 - Per-image x64 unwind metadata core and dependency repair

## What changed and why

M04-020 now has a bounded C# decoder for original registered PE32+/AMD64
runtime-function and version-one unwind metadata. `Validate` measures private
storage, `Bind` snapshots the directory and consumed unwind prefixes, and
`Lookup` revalidates the original module and retained bytes before returning a
half-open function range with its owning image base. Results are POD statuses;
the kernel path allocates no managed storage and publishes no usable partial
binding on failure.

Validation covers directory/table bounds, sorted nonoverlapping executable
function ranges, immutable unwind backing, opcode/operand lengths and register
classes, prolog/frame ordering, executable handler RVAs and bounded same-image
chains. The admitted subset is explicit: version one, at most 2,048 functions,
at most 32 records per chain, listed same-image chain identities and save-only
secondary nodes. Language-specific handler data is represented only by its
start; it has no format-independent admitted length.

The backlog dependency audit removed M04-020's artificial TLS prerequisite in
favor of accepted M04-011 (#80). Full casts/unboxing (#86) now wait for actual
exception handling (#90) as well as dispatch (#85); #90 still waits for this
metadata slice and owns its nonthrowing exception matcher. This avoids a cycle
through casts, delegates, TLS and exceptions. M03-010 (#67) retains #66 as its
blocker, but its stale statement that ExitBootServices was never called and
generic acceptance text are replaced with concrete original-owner post-exit
requirements. These are scope/dependency corrections, not issue closures.
