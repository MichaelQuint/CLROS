# Step 1021 - Retain the original EFI image with section permissions

## What changed and why

Issue #64's owned hierarchy must retain the executing image and its static
allocator metadata, boot records and copied ACPI buffers. Add
`FirstExitImageMappings.WriteRanges` in the existing first-exit core. It derives
header and section intervals from the successful loaded-image capture and typed
identity-mapping evidence. Headers and immutable data are RO/NX, code RX, and
writable data RW/NX. Gaps remain absent; zero-filled section data is included.

Admission is bounded to x64 PE32+ EFI applications with 4-KiB section alignment,
up to 16 sections, the retained mapper's page limits, and a readable caller-owned
image. It checks header/table extents, raw/virtual sizes, ordered nonoverlapping
page ranges, permissions and executable entry-point coverage before output writes.
Writable-executable, unreadable, noncached, overlapping or malformed sections
refuse. Output cannot alias the image. `Contains` checks required object/function
intervals against an already validated range list without granting ownership.

The PE layout and section size rules follow Microsoft's
[PE format specification](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format).
The narrower section count, alignment and permission policy is CLROS admission
policy, not a general PE loader. Existing TypeManager metadata registration is
unchanged; this reader establishes page permissions without requiring runtime
registration or exposing that registrar's private state.
