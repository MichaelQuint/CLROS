# Step 1568 - Exact mount failure and preserved zero-timestamp compatibility

## Summary

Fresh original r05/r06 guests pass the prior memory admission, descriptors and
Block.Start, then fail mounting the FAT webroot. Bounded failure diagnostics and
independent raw extraction identify an all-zero write timestamp in the first
preserved EFI directory entry. Only that exact timestamp pair now maps to
unspecified metadata. All other malformed date/time pairs still reject.

## Why

R06 emits `stage=7 phase=6 blockFailure=1 fsFailure=26 submitted=36 completed=36
copied=36 ioActive=0 arraySector=32 header=1 partition=1`. Block status1 is
Success; FS status26 is CorruptDirectory. This is34 GPT reads, BPB, then the first
root-directory sector. Independent extraction computes ESP2048, data/root4096
and reads slot0 EFI(cluster3, attrs16, date0/time0), then OS with the same zeros.
Imported app/private entries use date33. VFAT parsing accepts EFI, but the
calendar conversion rejects1980-00-00 before lookup reaches app.

The expert independently reproduced this from the held source/image without
edits or builds. A deterministic valid-date base writer was considered; the
selected explicit compatibility policy preserves existing boot metadata instead:
only date==0 && time==0 yields ModifiedSeconds=0. It is not a claim that zero is
a calendar write date. Other date/time validation and all namespace/data guards
stay intact. The expert's bounded read-only review found no concrete flaw in
this chosen policy. The runtime still uses the existing UTC admission assumption.
