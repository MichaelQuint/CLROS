# Step 1209 - Heap ownership repair qualification (in progress)

## Summary

Implement the #708 brk/MAP_FIXED ownership repair in the existing C# memory and
startup services. ReserveHeap creates a private heap tag; general mmap never
creates it. Region copy/split/coalescing and audit preserve and distinguish that
tag. ResizeHeap checks the entire old/new active prefix before changing pages.
Owned shrink releases backing while retaining sparse reservation and dump policy;
ordinary fixed maps and unmaps still relinquish replaced heap ownership.
Focused host checks and development mixed-operation/fault guests pass. Original
compiled ownership/ABI changes receive scoped review. Frozen full-host, three
fresh qualification guests and affected ancestors remain pending; no issue closure.

## Why

Independent step1207/#708 review reproduced separately allocated storage becoming
writable heap after brk growth. Current source reproduced the exact failure
before changing production code: brk returned H+8192 instead of H after a fixed
RW page at H+4096 received sentinel 0x5a and was made read-only. Auditing page
tables alone could not distinguish allocator ownership. Keep general fixed-map
semantics while rejecting implicit reclaim of unrelated VMAs or lost holes.

## Evidence boundary

Host-tested and development-guest transactional allocator ownership in the
bounded single-CPU memory model. Replacement/unmap of an active heap prefix poisons subsequent brk
changes until ownership is legitimately restored; brk does not recreate lost
reservations from unrelated mappings or holes. This admitted restriction is
explicit, not broad Linux compatibility. Development guests prevent the exact
ownership/protection defect; frozen native/full acceptance, upstream Hello/runtime, application GC/EH, Kestrel,
numbered gate, cloud or production qualification follows.
