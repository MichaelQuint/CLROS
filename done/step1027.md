# Step 1027 - Prepare the original EFI adapter for the first real exit

Issue #64 / draft PR554. Isolated adapter preparation, not an enabled or executed
real ExitBootServices path.

## What changed and why

Added `M03FirstExitAdapter` inside `EfiEntry.cs`, behind a symbol absent from the
project. It captures original EFI entry arguments once, requires successful
original M01 image/allocator state and published ACPI copy, allocates bounded
code/data/table storage below four GiB, and composes the existing owned arena,
mappings, firmware binder and terminal transition.

The adapter reads CPU/PAT/CS state through bounded emitted queries, prepares
owned main/IST stacks and descriptors, publishes checked instruction bytes and
configures owned COM1 before entry. Its only real EBS path is the existing
bounded coordinator from the new owned stack. Success transfers to native
permanent adoption; diagnostics/fault callbacks use owned state. Callback
returns terminate in the native entry/adoption/fault stubs. Pre-entry failures
may report through firmware; allocated pages remain reserved until VM teardown.

Review found that the installed NativeAOT stack-probe helper remains in M01's
separate code page. The adapter obtains that original page from successful
stage-one state and checks its 27 helper bytes. Retained mappings now optionally
include this RX page, rejecting malformed extents and overlap with every other
allocation. The real adapter always supplies it; host compositions without an
installed helper can omit it. Inventory capacity increases from 24 to 25 ranges;
table/page limits remain unchanged.

Compile guards require original image/allocator/ACPI adapters and reject
intervening owned paging, managed heap, controlled-exit and terminal exception
probes. The normal project does not define the new symbol. Shared integration
must still admit its central probe policy, explicit sources and producer/runner.
