# Step 754 - IPv4 neighbor route diagnostic marker

## Summary

Added a caller-owned IPv4 neighbor route plan diagnostic formatter for Gitea
issue #712. The formatter serializes initialized `Ipv4NeighborRoutePlanResult`
metadata into a stable `IPV4_NEIGHBOR_ROUTE status=` marker without managed
references in the formatter result.

## Why

Phase F networking needs compact host-testable diagnostic markers for route
planning evidence. This step makes cached-route and ARP-request route outcomes
observable without claiming live NIC routing, ARP retry, sockets, FetchApp, or
Kestrel readiness.

## Files changed

- `src/OS.Kernel/Net/Ipv4NeighborRoutePlanDiagnosticFormatter.cs`
  - New no-allocation caller-owned formatter for
    `Ipv4NeighborRoutePlanResult`.
  - Reports route/action/cache/ARP/packet statuses, bytes written, cache
    count/capacity, and cached target MAC metadata.
  - Rejects default/uninitialized results and unknown route/cache/ARP/packet
    enum values before formatting.
  - Reports required and available byte counts for short destinations without
    partial writes.
- `tests/OS.HostTests/Ipv4NeighborRoutePlannerTests.cs`
  - Added formatter coverage for cached-route markers, ARP request and failure
    markers, short destinations, default and unknown enum rejection, and
    no-managed-reference result metadata.
- `docs/networking.md`
  - Documented the new marker, test coverage, and host-tested boundary.
- `done/step754.md`
  - Recorded this evidence step.
