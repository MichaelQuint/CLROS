# Step 1232 - Host TLS ownership and guarded reap

## What and why

Implements the host stage of M09-010/#192 on branch
`codex/m09-wait-address-tls`, parent `74994226500182c9e4337f768c784ffa51ecadbd`,
under draft PR #732 and the same owner as #191. Both issues remain open.

The accepted x64 context already carries FS and user-GS; kernel-GS remains
CPU-owned. `ThreadLocalStorage` adds fixed caller-owned metadata over the
qualified lifecycle table, without replacing that context ABI or adding a
managed thread-static implementation. Bases must already be initialized before
the worker is published. Bind authenticates a fresh Ready/Entry generation,
dedicated private page subpool, exact base/extent and disjoint known resources
before dispatch. Fresh owner/root/kernel-GS and saved base/FP admission are
rechecked before transfer. No MSR, hardware register or native transfer occurs.

Reap uses the existing lifecycle supervisor/queue/pin guards, then scrubs only
the declared TLS spans and advances/retires its own binding generation. Active
observed FS/GS references reject before any mutation. A failed or bypassed
lifecycle reap retains TLS backing and cannot report a successful release.
Mapped storage, actual fresh observations and revoked external/native references
remain explicit trusted-caller obligations. No pages are implicitly freed.
