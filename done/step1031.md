The diagnostic/fault combination fits its 32768-byte reservation. Frame sums
include constant stackallocs and four levels of the only recursive page walker;
the walker descends exactly one level per call and rejects repeated tables.
Native call overhead is deliberately counted conservatively, including overlap
with compiled return-address accounting. Firmware bodies are not assigned a
made-up bound: available space exceeds the UEFI x64 128 KiB requirement.

The unmanaged boundaries pass entry context in RCX, transition/context in
RCX/RDX, and fault frame/context/CR2/CR3 in RCX/RDX/R8/R9. Linked callbacks preserve
those inputs across local one-byte runtime transition helpers. The emitted
callers provide shadow space and alignment. Terminal stubs never return to their
caller; descriptor RETFQ is a local CS refresh, not a firmware return. Checked
port callbacks are local IN/OUT leaves. Linked diagnostic/fault graphs contain no
firmware call, allocation, TLS, class initialization or runtime import.

Preparation writes and reads back the complete vector/entry/adoption/port bundle
and page tables before calling the serializer. The actual linked serializer
matches its admitted 20-byte PUSH RBX / CPUID / cookie / POP RBX / RET sequence
in RX, nonwritable PE storage and the existing object hash. There are no later
code writes before invocation. The owned root maps the complete original image,
adapter/allocator/copied ACPI, contexts, code, page tables and stacks with guard
pages excluded. The seven existing guest cases retain their development boundary.

Interrupt ordering was reviewed explicitly: final firmware calls retain the
firmware root and IF=1. After success, only local bookkeeping/copies precede the
terminal continuation's CLI/CLD. Firmware IDT/GDT remain in place until the bridge
LIDT. The bridge uses the admitted firmware CS and IST0; the owned GDT retains
that CS alias across LGDT. After segment setup and LTR, the final IDT uses owned
CS8 and NMI/DF/PF ISTs. Descriptor readback precedes clearing PGE and loading CR3.
There is no STI or restoration path. Before the bridge is installed, firmware
still owns exception/NMI delivery; CLI does not eliminate those events. No memory
is reclaimed during this window. This ordering does not prove all firmware
handlers, asynchronous nested faults, or arbitrary hardware behavior safe.
