# Step 1288 - Owned ELF data permission changes for NativeAOT startup

## Why

Original-runtime r14 reaches the real guard-stack cookie initialization and
fails mprotect(`0x533000`,4096,RW) with EINVAL. The pinned original Linux trace
performs RW/getrandom/R on this page. Original debug symbols identify
`__security_cookie` at `0x5334f8`,size8; original disassembly at
`0x41c275`-`0x41c2c0` confirms the permission calls and random-byte store.
Pinned upstream [InitGSCookie](https://github.com/dotnet/dotnet/blob/820230c386db5b0106c5430b3e5aee92a7826bf5/src/runtime/src/coreclr/nativeaot/Runtime/startup.cpp#L187)
requires exactly that readonly-data transition. This is application runtime
startup; it introduces no kernel EH or executable-code mutation requirement.

## What changed

The existing memory service receives an explicit default-zero owned ELF
virtual/physical envelope. One active contiguous permission override supports
R/RW on a single original non-executable user-data mapping. Original static
mapping provenance remains immutable; composite audits and every dynamic rebuild
retain the override. Unsupported competing/partial changes fail atomically.

The default-off M16-009 prerequisite profile derives authority from the retained
loaded ELF plan/backing, excluding its separately mapped initial stack and
supervisor pool. Drained-owner teardown explicitly restores image protection
after dynamic unmap, then audits the original static inventory before scrubbing
and any owner-end witness. Existing dynamic and physical quotas remain.

`RestoreImageProtections` returns0 on success and negative errno on rejection.
It requires a detached mutation guard and the caller's inactive-root authority;
it preserves image bytes and remaining dynamic ownership. Full dynamic unmap
does not implicitly restore an outstanding image override. Combined inventory
overflow rejects before live publication, including later mmap while an image
override is active.
