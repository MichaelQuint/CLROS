# Step 1292 - Bounded application resources and first strict application captures

## Why and changes

Step1291 reproduces genuine backing exhaustion: a 1024-page commit has only
1020 free pages. The unchanged four-worker Hello separately hits its mechanical
128-IRQ limit. Worker capacity is not a sufficient application-resource policy.

- M16-008 and its children select application limits from the validated
  manifest: a main stack of at least 1 MiB or more than eight workers admits
  8192 backing pages, 8192 IRQ epochs, 16384 supervisor steps and at most
  300 seconds of genuine monotonic HPET time. Small mechanical policies retain
  4096 pages, 128 epochs and 512 steps. Actual worker counts do not change.
- The 32 MiB pool remains one exclusive allocation, represented by two
  4096-page retained mapping spans. Only the selected pool may exceed the
  startup allocator's previous bound. Retained declaration capacity becomes
  40 and total declared mapped-page capacity becomes 12288; the per-range
  4096-page limit and 55-page table arena remain fixed. Both physical backing
  aliases are validated and excluded from the independent user root.
- The same production-service replay now admits the formerly failing commit
  with the application pool: backed pages grow from 3076 to 4100 and the
  resulting leaf is genuinely writable. The old 16 MiB negative stays atomic.
- All upstream application consumers require exact budget start/end records,
  real nonregressing epoch times and completion before expiry. Synthetic
  four-worker observations pass 129 actual modeled IRQs without changing
  capacity. Missing, stale and expired records reject.
- The common memory model retains original ELF executable flags and one exact
  temporary R/RW data window, preserving immutable original provenance. Code,
  stack, gaps, competing windows and W+X reject. No-op image protection skips
  a borrow check; an actual change still rejects while borrowed.
- Consumers check monotonic/coarse clock results and the observed getcpu/309
  ENOSYS fallback. False getcpu success, EFAULT substitution and an unknown
  syscall still reject. No kernel syscall is added or stubbed.
- Hello's consumer also admits the observed uncontended mutex path, where
  neither main wait nor finalizer wake needs a futex syscall. Both children
  must still execute, install their masks and park their real futex/pipe waits.
  Contended wait/wake and wake-before-wait controls remain. Removing either
  child's actual wait rejects.

No application source, ELF, producer, publish settings, requested waits,
dynamic-region quota, 128-range user inventory or 128-page user table arena changes.
