## Why it changed

The unchanged pinned Hello requests 8,234,266,624 bytes with PROT_NONE. The
previous 4-GiB virtual policy cannot admit that reservation, irrespective of
physical RAM. The user policy now ends at 64 GiB, still within PML4[0] and
four-level canonical addressing. Kernel identity mappings, table roots and
actual backing retain the qualified physical bound below 4 GiB. Dynamic
anonymous ownership occupies the separate 4..64-GiB window.

`LinuxMemoryServices` uses caller-owned physical pool, static mapping inventory,
live tables and separate candidate tables. Virtual ownership is independent
of pool/backed-page and table/leaf quotas. PROT_NONE reservations create no
backing or tables. Accessible pages have genuine encoded USER leaves and
zero-filled backing. Partial protect/unmap split ownership; fixed anonymous
PROT_NONE replacement discards old pages, while mprotect(NONE) retains data.
Freed/reused pages are scrubbed. Candidate construction/audit precedes live
mutation. W+X, unknown flags, overflow, overlap, stale roots and resource
exhaustion fail without changing target tables, pool data or ownership.

The backend admits at most 64 final extents, 4096 pool pages and the existing
128-table/32768-total-leaf limits. Two extra provisional extents allow partial
splits and coalescing without false ENOMEM. Identical protection calls avoid
fragmentation. MADV_DONTNEED eagerly zeroes accessible ranges without claiming
physical reclamation; inaccessible ranges release their backing. Unknown advice,
file/shared mappings, demand paging, SMP and broad Linux compatibility remain
unsupported.

The owner must run on a separate kernel root, keep the target root inactive
while mutating its tables, then reload/publish CR3 before user resumption.
No hardware publication authority follows from these host APIs. The backend
is included and source-admitted in the no-stdlib EFI C# compile closure, but
not called by the live adapter. Existing one-use/64-call policy is preserved.
