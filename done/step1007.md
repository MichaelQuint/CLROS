# Step 1007 - Prepare the compiler-object collection diagnostic

The existing default-off GC-static EFI diagnostic now contains the #82/#552
collection exercise. Its existing profile first binds one 5520-byte collecting
owner on the original retained page, then materializes the original compiler
static base. The earlier plain-object, static object/null stores, and five stack
canary checks remain. A new genuine fixed class contributes one compiler GCDesc
reference series and constructor/accessor/store code.

After the original checks, a bounded graph routine creates a parent/child chain
and an unreachable two-node cycle. Temporary managed locals leave scope before
explicit collection. Four collection operations exercise:

1. Static-root chain and an explicit prior receipt survive; two cycle nodes die.
2. A real `new` reuses a dead node's address with a new identity, the old receipt
   rejects, and replacing the static root makes the former chain/prior scalar die.
3. Clearing the static field makes the replacement die while the static base stays.
4. A final real allocation reuses the first free gap and survives a repeated
   collection with no reclamation.

The existing checked scalar-store thunk validates seven exact graph/static stores
against original live receipts and compiler field geometry. Mutators and
collection do not overlap; no concurrent barrier/card-table support is implied.
Five additional read-only stack checks preserve the existing owned-stack contract.
Nine ordered `M04_COLLECT` records (stages 0..8) describe metadata, references,
collection counts, actual reuse identities, high-water/count and stack canaries.
The final allocator observations are eight allocations and 176 high-water bytes;
these are assertions awaiting guest execution, not observed guest results.
